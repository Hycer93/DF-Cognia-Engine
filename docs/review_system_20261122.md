## 1. 推理模块（cgraph / F 系 / minloop）

### ✅ 强点

- **两条执行管线职责清晰**：
  - `Engine.run`：固定骨架链，**O(1) token 增长摘要传递**（不是全量上下文重灌）。
  - `run_atomic`：邻接表调度器，具备**四通道退出**（terminate_suggest / llm_terminate / collapse / max_steps）、`MAX_VISITS` 软去重、`collapse` 上限、24 步最大深度封顶——是真实调度实现，**非 demo 原型**。
- **F00 → F10 → F20 → F40 → F50 整条主链路均有实现**，不是纸面设计：
  - F00 现状锚定、F10 分支发散、F20 权重层（w=(1+δ)^β·C·F·R·D）、F40 逆向回溯（BFS + Ω(x) 约束）、F50 聚合层（Y_hat=ΣW_k·Y_k，S_T 禁平均保留原生清单）。
- **记忆写入闸门三档枚举（绿/黄/红）封闭**（`skill_memory_gate.py`），具备真实安全边界，非自由文本。

### 🚧 软点 / 缺口

- **F 系闭环断层**：F30 未实现；**F60 forward_check 仅完成第一环 n-gram 字面关键词校验**；docstring 约定的第二环「深度正演复用 `minloop.verify`」**尚未落地**。
  - **后果**：名义上「逆求解 + 正演校验闭环」，实质只做**文本字面覆盖**，没有**图语义层面的结果校验**，无法自证推演输出是否成立。→ 对应待办 **#A**。
- **`executor.py` 仍为 544 行大文件**：P2-2 做过部分拆分，但主执行器依然臃肿。
- **两套调度并存**：`ChainExecutor` + `RouterAtomic`。属于设计选择，但**缺少隔离契约文档**，长期存在双维护成本、架构熵增隐患。→ ⚠️ 架构熵增。

## 2. 记忆模块（memory_judge / corpus_store）

### ✅ 强点

- **hold 待审池完整闭环**：四档判定 → hold 入 pending 池 → `review_holds()` 复审转正；新增**跨进程锁、原子 JSON 写、DB 事务退避重试、WAL 显式化**；夜间流水线自动消费（E-hold复审），**不再只进不出**。
- **sqlite + jsonl 双写治理严谨**：具备 `dual_write_errors` 审计、`shadow_regress` 双路 diff 对账；数据一致性保护完备。

### 🚧 软点 / 缺口

- **桩—LLM 双通路缺少一致性对照测试**：
  - `JUDGE_USE_LLM=1` 默认走 LLM 语义判定；故障 fallback 进入规则桩。
  - 现在两套各有回归（`memory_judge_stub_regression`、`memory_judge_llm_regression`），但**没有专门的对照测试**：同一输入下，桩与 LLM 输出是否显著分叉。
  - **风险**：入库闸门行为在正常模式与故障降级模式下可能发生**不可预期的跳变**，没有自动化手段捕捉。→ 对应待办 **#B**（成本最低、收益最高）。
- **巨型单体文件风险**：`memory_query.py`（926 行），四维加权、反问门分层、时间窗、治理后置**全部聚合于此**，是维护风险最高单点。→ ⚠️ 架构熵增。
- **悬空资产：`topic_layer`（556 行）默认关闭**：
  - `topic_enabled()` 开关默认 `False`，大量代码长期不跑；二选一决断：**补齐实证开启，或归档删除**。长期挂着会造成认知负担。→ 📌 待决断资产，对应待办 **#C**。
- **主观反馈信息缺口**：回执、认可/不认可类对话现在全部 `discard` 丢弃，**态度元信息直接丢失**；记忆只保存客观事实，不留存人类对记忆的评价（#11 候选需求，尚未立项编码）。

## 3. 跨模块系统性风险

### 59 处 `except Exception` 大范围捕获

- **设计意图**：优先保证管线不中断，故障降级（"异常不炸链路"是架构哲学）。
- **双刃剑**：过往 P0-1 JSON 解析崩溃事故，就是此类兜底保护下**被掩盖**的教训。
- **纪律要求**：**不是要删掉 try-except**，而是强制「**降级必留痕**」——所有降级路径必须落审计日志，**禁止裸 `pass`** 静默吞错。

### 测试广度充足，但深度分层要区分

- **广度**：29 个 audit、12 个 core、7 个单测，数量充足。
- **深度分层**：大量 E 系夜间冒烟属于「**不崩溃级校验**」——仅断言 `ok=True`、出口通道合法；**不等于断言业务行为正确性**。
- **缺口**：完整 **E2E**（对话输入 → 路由 → 推演 → 记忆闸门入库 → 检索回捞）的**强校验用例数量偏少**。

## 4. 最高优先级三件待办（不混入本轮闭环，作为后续立项候选）

> 按价值权重排序：**三选一或串行做，不在当前迭代编码**。等待优先级裁决。

### #A — F60 第二环深度正演（复用 `minloop.verify`）

- **收益**：补齐推理「逆求解—正演自证」闭环，解决**推演无法自证对错**的核心短板。
- **风险**：中等。改动集中在 `collab_pipeline` 与 `minloop` 调用。
- **不处理后果**：F60 只是字面关键词筛查，正演校验只是**名义闭环**。

### #B — 新增桩—LLM 判定一致性对照回归

- **收益**：捕捉同一输入下两条通路输出分叉，管控记忆入库闸门降级时行为跳变风险；**成本低、收益高**。
- **风险**：低。纯 `eval/audit` 测试，**不改动生产逻辑**。
- **不处理后果**：LLM 故障降级时，入库行为可能**无声漂移**，缺少自动化告警。

### #C — 对 `topic_layer` 做决断：实证开启 或 归档删除悬空代码

- **收益**：消除 556 行默认关闭的悬空资产，降低代码库认知负担。
- **风险**：中等。若选择开启需全套回归验证；若删除要做 git 历史留存。
- **不处理后果**：模块长期休眠，**没人确认是否还能工作**。

## 5. 边界说明

1. **本评审是现状定性，不是整改承诺**。三件待办需另行优先级裁决后单独立项，不混入已完成批次。
2. **「不崩溃级校验」≠「业务行为正确性校验」**：E 系冒烟覆盖的是"链路能跑通、出口合法"，不代表"推演结论正确、入库判定正确"。两者不可混淆，评审结论中的 🚧 均指后者。
3. **59 处 `except Exception` 是工程权衡，不是缺陷本身**：正确的应对是「降级必留痕」的纪律，而非简单删除异常捕获。删除会引入崩溃风险，得不偿失。
4. **旧快照记忆已过时**：早期记忆文件提到 `topic_hold` 池、`topic_layer` 为主链路等，与当前工程（`memory_judge` 四档判定、`corpus_store`）存在代差。本评审以代码为唯一事实源。
