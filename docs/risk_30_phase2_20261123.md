## 一、derived_only 标记存储方案（收敛项①）

### 1.1 现状勘查

**关键事实 A：DB 已存在 `status` 列，但 jsonl 不含 status。**

- DB `core_memory_card.status`：`active` 318 / `deleted` 2 —— **有活性区分**。
- jsonl `memories.jsonl`：320 条 **status 全为 None**；tier 已随 #29 留存（active 283 / precedent 37）。
- 即：**jsonl 是「状态丢失」的审计导出流，DB 才是唯一带 status 的真相源。**

**关键事实 B：`atomic_store` 现有查重读 jsonl，非 DB。**

`memory_organize.py:239` `load_memories()` = `_load_jsonl(MEMORIES_JSONL)`；`atomic_store` L114 的 full_hash 查重、以及未来 P0 语义查重若复用同一 `load_memories()`，池子就是 jsonl 全量 320 条（含 2 张 deleted + 37 张 precedent），与 DB 口径（status=active ∧ tier=active = 280 条）**不一致**。

**关键事实 C：`dfcp_tag` 是 JSON 文本列，可直接挂 `derived_only`，无需 ALTER。**

DB `dfcp_tag` 实测存 `{"domain":"001-003","behavior":"Ht","relation":"H","memory_class":"strategy_evolve"}` —— 标准 JSON 序列化字符串。追加 `"derived_only": true` 与现有 `memory_class` 同级即可，**零 schema 变更**。

### 1.2 三方案对比

| 方案 | 载体 | 改表 | 读取兼容 | 过滤实现 | 审计可查 | 结论 |
|---|---|---|---|---|---|---|
| **A（采纳）** | `dfcp_tag.derived_only=true`（JSON 内嵌） | ❌ 不改 | ✅ 旧代码忽略未知键 | 读接口 `tags.get("derived_only")` | ✅ DB 列可查 | **首选** |
| B | 新增独立列 `derived_only INTEGER` | ✅ ALTER | 需迁移+回填 | 直接列过滤 | ✅ | 备选，仅在 A 有读取性能瓶颈时 |
| C | 复用现有 `tier`/`weight` 语义 | ❌ | ⚠️ 语义污染（tier 表活性层次，非派生标记） | 易混 | ⚠️ | 否决 |

### 1.3 全链路兼容性核对（方案 A）

| 链路 | 是否读 dfcp_tag | 影响 |
|---|---|---|
| `schema.validate_memory_tags` | 校验 5 维，**不校验未知键** | 追加 `derived_only` 不触发拒收 ✅ |
| `_write_card_to_db` | 整包 `json.dumps(dfcp_tag)` | 自动带入，无需改 ✅ |
| 检索/`memory_query.load_memories` | 反序列化 dfcp_tag | 旧口径忽略未知键，新口径可读 ✅ |
| E4 审计 | 读 `repro` 判定 derived | 可加 `derived_only` 交叉校验 ✅ |
| 冲突判定 `classify_and_link` | 读 summary/entity，不读该键 | 无影响 ✅ |

**风险残留**：检索/事实推理链路**当前没有统一读取封装**把 `derived_only` 的 detail 挡掉。若不封装直接改，则 derived 卡 detail 会泄露到业务层（违背三层语义）。

**缓解（P1 强制项）**：新增统一读取函数 `read_card_detail(entry, purpose)`：`purpose in {"search","reasoning"}` 且 `dfcp_tag.derived_only` → 返回 `None`；`purpose in {"dedupe","audit","governance"}` → 返回完整 detail。业务侧一律走该函数，禁止直接 `entry["detail"]`。

## 二、P0 语义查重性能（收敛项②）

### 2.1 实测数据（status=active ∧ tier=active，池 280 条）

| 环节 | 实测耗时 | 说明 |
|---|---|---|
| 冷启动全池 warmup | **1.32s**（280 条批量） | 进程首启一次性 |
| 单条新卡 embed（缓存命中时） | ~0s | 重复文本直接取缓存 |
| 单条新卡 embed（冷却 miss） | **8.5ms** | 单条 ONNX 推理 |
| 全池 280 条点积比对 | **27.5ms** | numpy 向量化 `pool @ q` |
| **单次入库增量总成本** | **≈ 36ms** | embed 8.5 + 比对 27.5 |

### 2.2 方案对比

| 方案 | 单次成本 | 优缺点 | 结论 |
|---|---|---|---|
| **全量比对（采纳）** | ~36ms | 280 条 numpy 向量化，一次矩阵乘；实现简单无漏检 | **首选** |
| 采样比对 | ~5ms | 省 30ms 但漏检（漏掉的非采样正本仍入库），违背查重初衷 | 否决 |

**结论**：36ms/次对记忆入库（本身含 LLM 调用，秒级）而言是**噪声级开销**，全量比对完全够用，无需采样。

### 2.3 性能告警阈值

| 指标 | 黄线 | 红线 | 动作 |
|---|---|---|---|
| 单次 P0 增量耗时 | >100ms | >300ms | gate_log 记 `p0_slow`；红线触发采样降级开关 |
| 池规模 | >2000 条 | >5000 条 | 提示引入 ANN（如 faiss）或分域比对 |

> 当前 280 条距黄线 2000 还有 7 倍余量，**短期无性能风险**。

### 2.4 缓存口径注意

`_cache` 是进程级常驻，**多进程/重启后失效**。方案：入库进程启动时 `warmup(active池summary)`（1.32s），此后增量 embed。若入库为短驻进程（每次新起），则每条都付 1.32s 冷启动——**需在段三确认入库进程生命周期**（memory_hook 是否长驻），否则需持久化向量表（复用 `trace_embedding` 表）。

## 三、P0 拦截误伤面（收敛项③）——本段最重要发现

### 3.1 阈值不可分的实测证据

用 `summary` embedding 实测 6 对（正确配对，来自附件）：

| 配对 | 相似度 | 定性 | P0@0.95 |
|---|---|---|---|
| PAIR1 | 0.980 | 真重复 | 拦 ✓ |
| PAIR2 | 0.954 | 真重复 | 拦 ✓ |
| PAIR3 | 0.952 | 真重复 | 拦 ✓ |
| **PAIR4** | **0.945** | **真重复** | **漏放 ✗** |
| **PAIR5** | **0.920** | **真重复** | **漏放 ✗** |
| **PAIR6** | **0.905** | **不同事实（反例）** | 放行 ✓（正确） |

**致命结论**：PAIR5（真重复 0.920）与 PAIR6（不同事实 0.905）**间距仅 0.015**。单靠 summary embedding 相似度，**不存在一个阈值能同时拦住 PAIR5 又放过 PAIR6**。0.95 既漏 PAIR4/5，若降到 0.92 则吃掉 PAIR6。

### 3.2 更深层错配：灰度正样本的路径归属是错的

| 样本组 | source_ref 实测 | 实际路径 | 能否作 P0（路径A）灰度样本 |
|---|---|---|---|
| #29 的 8 空壳 | 正本 `origin_corpus4: 归元仔人生.md 回填`（flash，detail 完整） | **路径 A** | ✅ 是路径A产物 |
| PAIR2-5（5张） | **`memory_gate; raw锚: session ...`** | **路径 B** | ❌ 路径B产物，P0 根本不作用于它 |
| PAIR6 反例 | `sim-test-a/b`（自检脚本） | 测试数据 | ⚠️ 非生产，仅作阈值反例 |

**立项书灰度判据「PAIR2~5 全部被拦」是根本性错配**：PAIR2-5 是路径 B 产物，P0 管的是路径 A，用它们验 P0 等于拿 B 的历史产物测 A 的闸门——**逻辑上不成立**：
- 路径B的卡不进 P0 查重池的「新写入」侧（它们已入库不在新写入流）；
- 即便把它们放进查询池，P0 只影响"未来路径A新写入"，与这些既有 B 卡的存留无关。

### 3.3 路径 A 的真实 P0 测试集（重建）

**唯一有效的 P0 正样本 = #29 的 8 张 derived 空壳 vs 各自正本**。实测（summary embedding）：

| 组 | 空壳 vs 正本 sim | P0@0.95 |
|---|---|---|
| 组1~8 | 1.000 / 1.000 / 0.981 / 1.000 / 0.986 / 0.994 / 0.953 / 1.000 | **8/8 全拦 ✓** |

**召回 8/8（最低 0.953）**——这才是 P0 在路径 A 的真实召回验证，且证明 **0.95 阈值对这些 derived 空壳有效**（因为空壳 summary 与正本 summary 高度同源，≥0.953）。

**精确率反例集**：需从**路径 A 真实写入**（memory_hook / judge_and_store / 回填）里抽样近 30 天卡，确认正常新增不被误拦。当前 PAIR6 来自自检脚本（sim-test），只能作为"0.905 是不同事实"的阈值下限旁证，**不能作生产精确率反例**。

### 3.4 误伤面清单（P0 在路径 A 上可能误拦的场景）

| 场景 | 触发条件 | 处置 |
|---|---|---|
| 同主题不同结论（如 PAIR6 类） | summary 前半句同、归因不同，sim 0.85~0.92 | 0.95 阈值天然放过，**安全** |
| derived 空壳与正本（本应拦） | sim≥0.953 | 拦住 ✓ 正确 |
| 真实新增近似主题（sim 0.90~0.95） | 边界带 | **漏放**（宁漏勿错，符合 §二原则3） |
| 模板句式碰撞 | 已由 bge 语义能力解决（段一 embed 自检） | 无风险 |

**结论**：P0@0.95 在路径 A 上「宁漏勿错」成立——最坏是漏放 0.90~0.95 的真重复（可接受，退化为现状），不会误拦不同事实。**唯一需盯的是 0.95 附近是否误伤**，灰度期全程日志观测。

### 3.5 开关、降级、审计、灰度观测策略（细化）

1. **开关**：`ENABLE_SUMMARY_EQUIV_DEDUPE`（config）三态：`off`（完全关闭）/ `dry-run`（只算只记不拦）/ `on`（真拦）。默认 dry-run。
2. **降级**：性能红线（§2.3）自动转 dry-run + `p0_slow` 告警；embed 模型加载失败 → 整体跳过 P0（记 `p0_unavailable`），不阻断入库。
3. **审计**：每次比对写 gate_log：`{ts, new_summary_preview, best_inst_id, best_sim, verdict, elapsed_ms}`；dry-run 也写（标 `dry=true`）。
4. **灰度观测**：dry-run 跑 1 周，统计：命中数、命中分布（0.95~0.97 / 0.97~0.99 / >0.99）、误拦人工抽样。**达标线**：8/8 空壳召回 + 人工抽 30 条命中确认无误拦，才转 `on`。

## 五、段三前必须解决的前置项（段二结论）

1. **【阻塞】查重池口径统一（R1）**：P0 语义查重的比对池必须是「DB status=active ∧ tier=active」（280 条），与现状 full_hash 读 jsonl 的口径分裂需在段三方案中一次性统一。建议新增 `load_active_pool()`（读 DB），P0 与 full_hash 同口径。
2. **【阻塞】灰度正样本集重建（R2）**：P0 正样本 = #29 8空壳 vs 正本（8/8 召回已实测）。PAIR2-5 移出 P0 判据（它们是路径B产物，转 #31）。PAIR6 保留作"0.905≠同一事实"的阈值旁证，非生产反例。
3. **【重要】`derived_only` 读取封装（R4）**：P1 落地前必须先建 `read_card_detail(purpose)` 统一入口，禁止业务层裸读 detail。
4. **【确认】入库进程生命周期（R6）**：段三确认 memory_hook 是否长驻，决定是否需持久化向量表。

## 六、段二结论

1. **`derived_only` 存储：采纳 `dfcp_tag.derived_only`（不改表）**，全链路兼容，唯一前提是 P1 同步建统一读取封装。
2. **P0 性能：全量比对，36ms/次，完全可接受**，无需采样；红线 300ms 触发降级。
3. **P0 误伤面：0.95 阈值「宁漏勿错」成立**，但**发现两处立项书硬伤**——① 灰度正样本 PAIR2-5 是路径B产物，不能验 P0；② PAIR5/PAIR6 间距仅 0.015 证明单一 summary 阈值不可分。**正样本改用 #29 8空壳（已实测 8/8 召回）**，PAIR2-5 移交 #31。
4. **查重池口径分裂（jsonl vs DB）是 P0 落地的前置阻塞**，段三方案必须先统一为 DB status=active∧tier=active。
