## 零、两个观察点实测结论（段四前置验证，已完成）

### 观察点 1：完整冷启动耗时（PreCompact 120s 超时挤压评估）

**实测（新进程从头，含 onnxruntime import）**：

| 阶段 | 耗时 |
|---|---|
| import（含 onnxruntime 首载） | 0.30s |
| model + tokenizer load | 0.12s |
| 全池 warmup 280 条 | 0.91s |
| **完整冷启动合计** | **1.34s** |

**结论**：1.34s 占 PreCompact `timeout=120s` 的 **1.1%**，叠加 LLM 会话处理（35~42s）仍余量巨大。**R6 首版走"每进程 warmup"零风险，B' 持久化向量非必需，维持优化项。**

### 观察点 2：memory_query.load_memories 读侧 tier 过滤差异

**实测**：

| 口径 | 条数 | 说明 |
|---|---|---|
| `memory_query` 读侧（status='active'） | 318 | 含 38 张 tier=precedent |
| 查重池 `load_active_pool`（status='active' ∧ tier='active'） | 280 | 排除 38 precedent |
| 差集（仅 query 有） | 38 | 其中 29 张有 detail、9 张 detail 为空 |

**结论**：读侧维持现状（318，宽口径=检索要能看到已降级旧版本供回溯），查重池严格 280（窄口径=precedent 不应拦新写入）。**口径差异是有意的，非 bug**。段四测试需固化"两口径不同是预期"的断言（防止未来误把两者统一）。

## 一、测试环境准备（fixture 设计）

### 1.1 隔离策略（沿用 e7_gate_regression 惯例）

- **不碰主库**：`shutil.copy(MAIN_DB, tmpdir/test_30.db)`，所有构造行注入临时库。
- **重定向目标**：
  - `memory_organize.MEM_DIR` → tmpdir（影响 `load_active_pool`、`_write_card_to_db`、`append_jsonl` 全部读写）
  - `memory_organize.load_active_pool` 内 `_db` 走 `MEM_DIR` 拼接 → 自动跟随
  - `embed_semantic._cache` → 每个用例前清空（`E._cache.clear()`），避免跨用例污染
- **清理**：`teardown` 删 tmpdir（`shutil.rmtree`）。

```python
# 夹具骨架（每个回归脚本开头）
```

```python
def mk_card(con, iid, summary, *, status="active", tier="active",
            detail="d", repro="situational", asset_class="knowledge",
            source_ref="test", dfcp_tag=None, full_hash=None):

        "INSERT INTO core_memory_card (inst_id, ts, full_hash, asset_class, repro, "
        "confidence, dfcp_tag, summary, detail, source_ref, tier, status) "
        "VALUES (?,?,?,?,?,?,?,?,?,?,?,?)",
        (iid, NOW, full_hash or ("h" + iid[-8:]), asset_class, repro, "L1",
         json.dumps(dfcp_tag or {}, ensure_ascii=False), summary, detail, source_ref, tier, status))
```

## 三、手动冒烟脚本（dry-run 链路快速校验）

```python

# 跑法: DF_SUMMARY_EQUIV_DEDUPE=dry-run python eval/audit/e30_smoke.py

冒烟校验项:
  S1 池加载: load_active_pool() 返回条数, 每卡有 inst_id/summary/full_hash
```

## 四、判定标准与预期输出

### 4.1 每条用例判定
- **U 单元**：函数返回值/DB 行字段精确匹配（阈值用区间，如 best_sim∈[0.953,1.000]）。
- **I 集成**：`atomic_store` 返回 status 元组 + 临时库实际行数变化 + gate_log 行内容三重校验。

### 4.2 日志校验要点（gate_log.jsonl）

| op | 校验字段 | 预期 |
|---|---|---|
| `skip_equivalent_derived` | best_sim, best_inst_id, new_summary, elapsed_ms | best_sim≥0.95；new_summary 截断≤120 |
| `p0_equiv_dry` | would_skip, best_sim | 命中时 would_skip=true |
| `p0_unavailable` | err, stage | embed 失败注入时出现（mock 抛错） |
| `p0_slow` | elapsed_ms, pool_size | mock 慢路径 >300ms 出现 |
| `warn_corpus_runtime_equivalent` | corpus_inst, runtime_inst, best_sim | P2 跨池等价时出现 |

### 4.3 关键阈值断言（固化，防漂移）
- P0 `SUMMARY_EQUIV_THRESHOLD == 0.95`（断言常量，防止低于 0.95 上线）。
- 8 空壳召回 best_sim 最小值 ≥ 0.95（实测 0.953）。
- PAIR6 sim ≤ 0.92（不达阈值，验证反例）。
