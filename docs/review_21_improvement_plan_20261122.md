## 〇、两处前提修正（立项前代码核实，与原始方案表述不同）

### 修正 1：Router **已经有** simple/medium/complex 三档分流，问题不是"没有分流"

- `router.py:48-51`：simple 直接走 `MANDATORY_NODES = [Aa, Eo, Jw]`（3 节点，Jw 出主链 → **实际仅 2 次 LLM 调用**）
- 原始方案说"simple/medium/complex 全部完整跑 heavy 主链"——**不准确**

**真正的问题**（核实后更精确）：

- 28 条历史评测路径长度分布 6~16 节点，**没有一条是 simple 的 3 节点路径**
- 说明被评测的题**全被判为 medium/complex**，即 classify 从没判过 simple
- 更严重：**medium 和 complex 走出的路径完全相同**（都 14 节点）——`min_weight=0.35 vs 0.2` 的差异在这张图上没有产生任何路径差异

→ **"无差别跑重链"的根因是"分档了但档位对路径长度无实际区分作用"，不是"缺分流"。** Q1 的真正价值应调整为：(a) classify 更准地判 simple；(b) 让 medium 真正裁出比 complex 短的路径（现在的 medium 名不副实）。

### 修正 2：Q2 语义降权收益极低，建议降为观察项

- 消融实测：主干边权 ≈1.83，旁支 ≈0.3-0.5，鸿沟 >1.2
- 语义系数乘在历史边权上：主干节点 ×0.5 后仍 ≈0.9，**远高于旁支**，无法改变主干选择
- 且 Q1 分流后 simple/medium 冗余链路已大幅缩减，Q2 边际收益更小
- **结论：Q2 与 Hebbian 同病——够不着主干。降为远期观察项，不投入主力。**

## 二、新增前置观测（本方案补充，强烈建议最先做）

### OBS-1：节点级意图贴合度观测（零风险埋点，先定位跑偏点）

- **问题**：方案假设跑偏发生在中段，但无数据支撑"跑偏具体从第几个节点开始"
- **做法**：`_walk_chain` 每节点产出后，用 `_llm_verify` 同款打分对**原始 user_input** 打一次贴合度，记入 trace
- **判读**：若贴合度随节点序号单调下降 → 证明"越跑越偏"，Q1 缩短链路是精准打击；若不下降 → 问题在别处，省下后续一堆优化
- **成本**：每节点多 1 次轻量打分调用（可离线批量，不影响线上）；或先只在离线分析脚本里做，不进生产链路

## 三、第一组：质量改进（解决意图稀释）

### Q1 Router 请求分流（必做，前提已修正）

- **simple**：已有 2 节点轻链，需确保 classify 能判出来（当前判不出）
- **medium**：真正裁剪（当前名不副实，与 complex 同路径）
- **complex**：保留完整 heavy 链
- **约束**：保留 MANDATORY_NODES=[Aa,Eo,Jw] 保底锚点；分流决策由 Router 复杂度判定输出；**每次分流结果写日志（simple/medium/complex 标记 + 实际节点数）**

### Q3 Summary 推理核对表（必做，输出层兜底）

```json
{
  "user_intent": "原始用户意图",
  "items": [
    {"node_id": "xxx", "content": "xxx",
     "relevance": "support|conflict|irrelevant", "comment": "对意图的影响"}
  ],
  "final_answer": "..."
}
```

- irrelevant 内容禁止混入 final_answer
- 整表写入 trajectory 轨迹日志，可复盘
- 调试开关 `FORCE_ALL_EVIDENCE`：强制全保留，防 LLM 误弃关键信息
- **补充要求（本方案加）**：relevance 判定应**独立于主链上下文**——用原始 user_input 单看每个 node 产出打分。否则 LLM 会把"自己跑偏的内容"也标成 support（自我审查失效风险）
- **作用**：守住对外输出底线；但不阻止中间执行无用节点，不解决耗时

## 四、第二组：性能优化（解决 12.6x 耗时）

> 核心真相：慢来自主链 13 次串行 LLM 调用，不是单次调用慢（单次图路由 17.4s < 裸模型 20.1s）。

### P-A 主链多节点 Prompt 合并（必做，收益最大）

- 多个连续主链节点的视角合并到同一 LLM 请求，一次调用输出多节点 analysis/deepen
- 业务逻辑、节点契约完全保留，trajectory 仍记每节点产出，只减网络 IO
- 强化 JSON Schema 校验；**单节点解析失败沿用老降级：单节点失效不打断整链**
- 控制 prompt 总 token 上限
- 预期：主链 13 次 → 4-5 次

### P-B 非关键任务移出阻塞路径（必做，方案 B1）

- **仍阻塞**：Router、合并后主链、Summary、verify 自检、**Jw 复盘**（保障 verify_ratio 即时供 Hebbian）
- **异步**：记忆闸门/归档
- 约束：异步失败必须 E4 告警，不能静默丢归档
- 取舍：Jw 不异步（避免 Hebbian 反馈延后一轮）

### P-C 分类任务切轻量小模型（增强）

- Router 复杂度判定、verify 意图自检 → 小模型
- 配置降级：小模型异常自动回退主力模型

### P-D 加深分支并行（增强）

- 仅用于互相无依赖的 deepen 分支；主因果链仍串行
- Python 并发约束：每线程独立 LLMClient、分支只读不写 MindGraph、并发上限 3-5（规避 429）、单分支超时不破坏主流程
- 局限：simple/medium 很少触发 deepen，提速有限；仅大量分支 complex 题明显

**性能综合预期**：阻塞路径调用数 → 7-8 次，整体耗时压到裸模型 3-4 倍。仍高于裸模型，**故 Q1 分流必不可少**。

## 八、迭代执行顺序（推荐，含本方案微调）

```
1. #20 记忆可观测性+合规（P1，最先）
2. OBS-1 节点级意图贴合度观测 ← 新增前置，先定位跑偏点
3. Q1 Router 分流（必做，收益直接）
4. Q3 Summary 核对表（必做，配 FORCE 开关 + 独立判定）
5. P-A 主链 Prompt 合并（必做，收益最大但风险最高，放分流后）
6. P-B 异步归档（必做）
7. P-C 小模型 / P-D 加深并行 / Q2 语义降权（增强）
8. #17 → #18 → #19 Hebbian 三部曲
9. 远期：复杂决策测试集
```

**微调理由**：P-A 放分流之后而非最前——合并 prompt 改变节点行为，若在无分流状态下先合并，等于在错误基础上做高风险改造。先分流缩小问题面，再合并更稳。

## 九、风险总清单

| 风险 | 缓解 |
|---|---|
| Prompt 合并致 JSON 解析故障率上升 | 保留单节点降级 |
| 异步记忆归档失败 | E4 告警，不静默丢数据 |
| 小模型分类出错 | 回退主力模型 fallback |
| 推理核对表 LLM 误判相关性 | 日志 + FORCE_ALL_EVIDENCE 开关兜底 |
| 慢的串行判分类环节（本次实测单题 >870s，后端延迟主导） | P-C 移小模型/本地收益最大 |
| 即便全优化完，complex 仍 3-4x | simple 必须走轻量分支 |
