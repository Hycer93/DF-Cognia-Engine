> 触发：E4 晨报报警 `DB↔jsonl 迁移漂移 +75 (db=320 vs jsonl=245)`
> 性质：数据一致性缺陷，非本轮 #20/#23 引入。纯数据对账诊断，未改任何代码。

- `core_memory_card`（DB）: **320** 条
- `memories.jsonl`: **245** 条（unique inst_id 245）

## 三、根因

### 主因：11-15「读源切换」后 jsonl 漏写、且无回补机制

- `git log`：**11-15 `9c011d4` feat(switch)! #31 读源切换至 SQLite 主库**。
- 切换后 `memories.jsonl` 被降级为「审计导出流」，注释写「写库失败**下轮增量同步补**」——但**夜间 `scripts/nightly_run.py` 的 STEPS 里并没有「DB→jsonl 回补」步骤**（已逐条核对 STEPS，只有 E1/E4/E5/E9/T1 等，无 sync/backfill）。
- 于是 11-15~11-19 期间：部分入库路径只写了 DB（`core_memory_card`），jsonl 侧漏写，且**承诺的"下轮增量同步补"从未实现** → 累积 68 条真缺失。
- jsonl 自身日期分布佐证：11-14 后 11-15~11-19 **完全空档**，11-20/11-21 才恢复零星写入（9+4），与"某段写入链路漏了 jsonl"吻合。

### 次因：7 条重复入库

- 同一 summary 文本以不同 `inst_id` 各存一份（jsonl 与 DB 各一份）。疑似早期去重（simhash/full_hash）在切换期有漏洞，或人工补录与自动入库撞车。

## 四、影响评估

- **功能影响**：当前读源已切 SQLite 主库（`DF_MEMORY_SOURCE` 默认 sqlite），**日常检索/问答不受影响**——DB 才是真相源。
- **风险点**：
  1. **应急回切失效**：若哪天 `DF_MEMORY_SOURCE=jsonl` 回切，会**丢这 75 条**（jsonl 里没有）。
  2. **E4 晨报常亮报警**：漂移非零导致每天的 +75 报警，掩盖其他真报警。
  3. **#20 Phase2 指标失真**：误归档率/demote 比等统计依赖 DB↔jsonl 对账基线，漂移不清基线不准。
