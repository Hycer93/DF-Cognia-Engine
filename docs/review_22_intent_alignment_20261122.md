## 一、要回答的问题

改进方案把 #22 定为 cgraph 线第一前置埋点，目的是用数据回答一个假设：

> **「意图稀释」是否随链路变长持续走低？** 如果是，那么 #23 缩短链路（Router 分流）就是精准对症。

在动手改 Router(#23) / 加输出兜底(#24) 之前，先用节点级贴合度打分验证这条因果链是否成立，避免在错误假设上做高风险改动。

## 二、方法（两套打分器，用户确认的并行方案）

1. **embedding 全量批量（方案 A）**：`memory/embed_semantic.py`（bge-small-zh-v1.5，CPU）对每个节点产出文本与原始 user_input 算余弦相似度。全量、零 LLM 成本、可批量。
2. **LLM 抽样校验（方案 B）**：复用 `executor._llm_verify` 同款提示，抽样十字段打分。用于校准 embedding 口径。

### 数据来源可行性（遵守用户约束）

- 探查 `data/trajectories/*.jsonl`：历史仅 `traj_raw_20261103_184035.jsonl` 含 3 条完整节点产出（thought_chain 按 `〔先想 · {label}〕` 分隔）。
- 尝试 `--live` 新跑与 LLM 校验：**当前后端严重降速（单题 >12 分钟、单次 LLM 60–90s）**，均超时终止。
- 遵约束「绝不重跑全部历史、NO_MEMORY=1 只跑 3-5 题、纯离线不改生产」，最终采用 **3 条历史样本 + embedding 全量**，LLM 校验列为环境限制未完成（见 §五）。

### 打分口径修正（关键）

首版用线性斜率判趋势，但分数是**锯齿波动**（各节点语义主题不同），单调性不可靠。改为双指标：
- 前 1/4 均值 vs 后 1/4 均值（宏观漂移）；
- 窗口平滑斜率。
- 判定：`Δ后-前 < -0.05` 或 `平滑斜率 < -0.008` = 下降。

## 四、结论与对后续任务的影响

1. **「意图稀释随链路变长」假设未获数据支持。**
   节点贴合度高低由**节点职责离字面 query 的距离**决定，而非链路累积漂移。方法论节点（隐性共识、内在怀疑、直觉锚定、上下文等价校验）天然离原始 query 远，属职责特性，不是跑偏。

2. **#23 Router 分流的价值需要重新定位。**
   分流真正收益在于**省 LLM 调用 / 降耗时**（已验证 12.6x 耗时 = 14.6x 调用数），**不应再以「治意图稀释」为立项理由**。分流改造（classify 判准 simple + medium 真正裁短）依然值得做，但目标改为性能。

3. **#24 输出兜底方向依然成立，但机制需改。**
   若质量确有问题，病根更可能是**低贴合的方法论节点其产出未被有效汇入最终答案（信息丢失）**，而非「越往后越跑偏」。#24 的核对表应从「纠偏」改为「保证低贴合节点的价值被保留/被引用」。

4. **不建议按原假设给 #23/#24 排高优先级工期。** 二者仍列 P1，但立项依据从「质量纠偏」修正为「性能 + 信息保真」。

## 五、限制声明（必须随结论一起读）

- **样本量 3 条**：结论定性看现象，不做统计显著性断言。趋势可用，但不能外推为普遍规律。
- **LLM 抽样校验未完成**：后端降速（单次 60–90s）导致超时，本次仅有 embedding 分数。embedding 仅反映**字面语义余弦**，对「方法论节点是否有效贡献内容」这一更高层问题无判别力——这正是 §四.3 需要 #24 用 LLM 核对表补足的地方。
- **embedding 口径**：低分 ≠ 无价值。方法论节点贴合度低是**预期内**，不能据此裁掉这些节点。
- **纯离线**：未改动生产 Executor，`_walk_chain` 线上链路零改动、零新增 LLM 调用。
- **建议补测**：环境恢复后，用 ≥20 题重跑 embedding + LLM 抽样，确认 3 样本观察是否成立。
