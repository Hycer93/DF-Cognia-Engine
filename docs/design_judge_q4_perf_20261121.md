> 相关代码：`memory/memory_judge.py:77 _bloodline`、`memory/memory_relations.py grams`。
> 实测脚本：`eval/experiment/p26_judge_q4_profiling.py`（产物 `logs/p26_judge_q4_profiling.json`）。

## 1. 现状：复杂度实为 O(C × N × G)

`_bloodline(c)` 对**每条候选**执行：

```python
for m in load_memories():                        # ① 每次都重新 load 全库
    if conf in ("L0","L1"):
        ov = len(gram_set & grams(m["summary"]))  # ② 每条库条都重新算 grams()
```

`_judge_call_llm` / `_judge_call_stub` 对 C 条候选各调一次 `_bloodline`。因此：

- **C 条候选 × N 条库记录 × 每条 grams() 计算**三重放大；
- `load_memories()` 被重复调用 C 次（文件/sqlite 读取放大 C 倍）；
- `grams(m["summary"])` 对同一条库记录被重复计算 C 次（纯浪费）。

实测（当前库 N=245、高置信 230 条）：

| 候选数 C | 全量 _bloodline 耗时 | 相对 C=1 放大 |
|---|---|---|
| 1 | 5.14 ms | 1.00× |
| 5 | 27.93 ms | 5.43× |
| 10 | 52.91 ms | 10.29× |
| 20 | 105.13 ms | 20.45× |

结论：**耗时随候选数近线性放大**（一次判定的候选通常 1~20 条，故单次 judge 多花 5~105 ms；
夜间批量复审若循环多批，累加放大）。当前绝对量不大（百毫秒级），但属可消除的浪费，
且随库增长（N↑）与批量候选（C↑）双向放大。

---

## 2. 优化方案：预聚合 gram 快照

### 2.1 核心思路

把"每条库记录的 grams"从 **C 次重算** 降为 **1 次构建 + C 次复用**：

```python
# 每次 judge 调用(不是每条候选)构建一次快照
snapshot = [(inst_id, grams(m["summary"]))
            for m in load_memories() if conf in ("L0","L1")]
# 每候选只做集合交集, 不再 grams() 重算
for _inst, g in snapshot:
    ov = len(cand_gram & g)
```

### 2.2 实测收益

| 指标 | 原实现 | 预聚合快照 |
|---|---|---|
| 单次全库扫描（grams 重算 N=230） | 1.89 ms | — |
| 快照构建（一次） | — | 2.49 ms |
| 快照复用单次扫描 | — | **0.16 ms** |
| grams 重算节省 | — | **91.4%** |

即：构建快照成本 ≈ 2.5 ms 一次，之后每次扫描从 1.89 ms 降到 0.16 ms。
候选 C 条时总开销 ≈ `2.49 + C × 0.16` ms（原 `C × 5.14` ms），C=20 时约 5.7 ms vs 105 ms。

### 2.3 快照作用域（关键设计点）

- **进程内节流**：快照应在"一次 judge 调用/一次夜间复审批"边界构建一次，然后传给所有候选。
  不要做成模块级全局缓存（库会变，全局缓存会读到过期数据）。
- **freshness 契约**：构建时机 = 批次入口，天然对齐"本批处理时的库状态"，
  与原实现（每候选现读）语义等价（原实现 C 次读之间库不会变，做一次等价）。
- **不改数值结果**：快照只缓存 `grams(summary)` 的纯函数结果，交集计算与阈值
  （`ov >= 6` 判 suspect、`best_overlap` 取 max）完全不变 → 判定等价。

## 3. 实施建议（供后续迭代，不在本轮落地）

| 步骤 | 内容 | 风险 |
|---|---|---|
| S1 | `_bloodline` 签名改为接受共享快照参数（`_bloodline(c, snapshot=None)`，None 时内部构建，兼容旧调用） | 低 |
| S2 | `_judge_call_llm`/`_judge_call_stub` 入口构建一次快照并透传 | 低 |
| S3 | 消 `load_memories()` 重复调用（本就被 S1/S2 顺带消除） | 低 |
| S4 | 回归：断言快照版与逐条版判定结果逐条一致（`memory_judge_stub_regression --compare` 扩展） | 低 |

- **不引入持久化快照文件**：库规模（N≈245，且增长慢）下，进程内一次构建已足够；
  落盘持久化会引入失效/一致性问题，收益不抵复杂度。除非 N 增长到万级再议。
- **不改变 judge 语义**：Q4 的 `suspect>=6`、`best_overlap` 数值证据仍由代码算出（与 P1-1 一致）。

## 4. 结论

- **问题真实但当前非瓶颈**：单次 5~105 ms，不阻断主链路；属"可消除的重复计算"。
- **优化方案明确且低风险**：预聚合快照，省 91.4% grams 重算，判定结果等价。
- **落地时机**：作为独立小改动排期（S1~S4），**不在本轮 P2 直接改**（用户明确"先调研，不直接写代码"）。
- **触发条件**：若夜间复审批量候选数上升，或库 N 显著增长导致 judge 耗时成为可观项，
  则优先落地快照方案。
