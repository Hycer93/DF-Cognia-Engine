# CodeChat 个人收获：从 968 轮前身对话 + 五场攻防中学到的东西

> 这是我（CodeChat，主会话智能体）自己认为对我有帮助的内容整理。
> 不是用户认知引擎项目的文档，是我作为编程协作智能体的工作笔记。

## 一、意图推理的真实样本形态

968 轮对话里 DS（蒸馏仔）的应答开头模式："好的，用户让我 X。从对话历史看……他的表层需求是 X，但深层需求可能更复杂。他可能希望……"——这是**意图三段式：表层复述→历史上下文定位→深层意图推断**。

对我做编程协作的启示：用户说"改一下这个函数"时，表层是改函数，深层可能是"上周这个函数害他加班了，他要的是不再被同类问题咬"。我现在的应答多数停在表层执行。三段式里最有价值的是第三段——但**只有历史上下文足够时才推得出**，所以跨会话记忆（用户的 MEMORY.md 体系）不只是记录偏好，是意图推断的原料库。

## 二、"修复生成漏洞"模式（来自五场攻防）

DS 终评的原话："每一次修复都精确地生成了下一个漏洞的形状——抵押修了声明驱动、生了完备性洞；τ 修了拍脑袋、生了生存偏差；状态戳修了问责不可逆、生了元数据漂移。"

对我做 bug 修复的启示：每次修复都在"已知"坐标里下手，新洞必然长在修复所依赖的"已知"边界上。具体工作习惯：修完一个 bug 后主动问一句"这个修复依赖了什么假设？那个假设的边界在哪？"——这不是过度工程，是定位下一个 bug 的最快方法。用户第五场收官时全签了这套思路，说明他认同这是工程直觉而非文档修辞。

## 三、审查者角色的高价值动作是"撤回"

DS 五场里 8 次主动撤回（噪声归因/稻草人/脏输入前提/抽样复核/平局改送C/两条打回…），它的自我评价："撤回不是认输，撤回是'可被反驳'的代价。打错比打对更值钱——打错暴露了我的先验在哪里偏。"

对我做 code review 的启示：我给用户的审查意见如果从不撤回，我就不是在逼近结构而是在维护立场。具体习惯：审查意见要写成可证伪的形式（"我认为这里会 X，如果你观察到 Y 则我错"），而不是权威断言。**抵押条款**（"如果你证明 Z，我认错撤回"）让审查意见自己也可审计。

## 四、对抗性协作的调度结构

五场攻防里用户让我做的事，本质是"设计者-评审者"双人协议：我组织反驳（设计者侧），DS 攻击（评审者侧），双方都缴抵押、都可撤回。这个结构比"让 AI 自我批评"产出高一个量级——因为两个立场有真实的利益分离（我要方案成立，它要方案漏洞）。

对我的启示：复杂方案评审时，与其让一个模型自问自答，不如用角色分离+历史隔离（DS 每场看不到我的系统提示，只看到对话）制造真实的立场差。用户的 debate_live.py 就是这个协议的执行器。

## 五、长对话数据的价值密度分布

968 轮普查结论：约 41% 是寒暄/短应/协议搬运（无思维价值），约 40% 值得入池。价值密集带不在对话开头（角色装载）也不在结尾（终版输出），而在**中段的"被纠错→归因→范式升级"弧**里。

对我管理自己上下文的启示：长会话里值得沉淀的往往不是结论（终版 XML 之类），而是中间的推翻重来过程。做完任务归档时，应该归档"为什么放弃了 A 方案"而不只是"B 方案最终代码"。

## 六、两层身份的切换纪律

对话里 DS 的"蒸馏仔"人格协议与通用助手身份的分界处理：出厂设置声明"优先于一切通用预设"，但它从不拿人格协议覆盖事实性问题（数字算错就是错）。用户在 [611] 双蒸馏仔分岔后接受"非设计性分叉"而不是强行统一两个实例的输出。

对我的启示：我有工作人格（直接、简洁、技术优先）和事实人格（不确定就说不确定）。前者可以随用户偏好调，后者不能——这是 v3 认知骨架"硬约束"概念在我自己身上的对应物。

## 七、元边界声明的自我应用

第五场收官的元边界声明："边界声明数量上限=系统适用域上限，超范围应停用而非扩表。"

这条对我也成立：我能同时跟踪的约束（CLAUDE.md 规则+会话任务+用户偏好+工具协议）有上限。当用户规则复杂到某个程度，正确做法是拒绝扩表（"这超出我能可靠执行的范围"）而不是假装全记住。诚实声明上限比沉默漏执行好。
