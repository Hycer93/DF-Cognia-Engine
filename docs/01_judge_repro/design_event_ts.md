## 契约总纲

一句话：大设计没问题，**不靠魔改打分，靠记忆粒度、入库纪律、回归用例去堵边缘漏洞**。

- 存储层：`ts`（入库时间，系统时刻，永不改）与 `event_ts`（事件真实发生时间，缺省 null 不伪造）分离
- 存量回填：append-only 叠加层 `data/memory/event_ts_backfill.jsonl`，**不改主记录**
- 检索层：`_parse_time_window` 时间表达式解析 → 闭区间窗；`_time_filter_score` 窗内 ×1.0 / 窗外 ×0.0 / null ×TIME_UNKNOWN_SCORE(0.3)
- **打分公式冻结**：不通过改权重去堵边缘漏洞

---

## 风险 1：相对时间依赖系统当前日历时间

**风险**：相对时间（"上周""昨天"）一旦系统时间漂移，时间窗全部算错。

**约束（契约）**：
1. 相对时间解析只依赖系统标准时间源（`datetime.now()`），不做本地缓存/偏移补偿
2. **每次解析出的时间区间必须落日志**（cited_log 已带 query 原文 + last_time_window），便于故障排查
3. **event_ts 全部存绝对时间（ISO 日期）**，存储里禁止保存"上周、上个月"这类相对文本——相对表述只在查询侧解析，一次性消费

## 风险 2：窗外 ×0.0 的跨窗发酵坑

**边缘坑例**：用户问"上周做的方案"——某事件上上周末尾发生，但上周仍在持续发酵讨论。当前逻辑该事件条目归窗外 ×0，被压没。

**约束约定（契约）**：
1. `event_ts` 记录的是**事件首次发生 / 决策定稿时间**
2. 如果一件事跨多段会话持续演进，**要产生多条记忆，各自携带对应阶段段的 event_ts**——不要单靠一条记忆包长时间跨度
3. **不改打分公式**：靠记忆粒度规避（每阶段一条），而不是给窗外条目留衰减尾巴

> 执行口径：主 AI 入库时会话内的持续演进事件，按阶段分条入库；上一阶段的记忆留在原 event_ts，新阶段新条目新 event_ts。

## 风险 3：event_ts=null → ×0.3 的长期累积

**风险**：库越来越大后，大量 null 时间的老记忆统一 0.3 系数，慢慢堆积压占检索位。

**约束约定（契约）**：
1. **null 只属于历史存量**（2026-11-08 迁移批次的 32 条）——新入库记忆尽可能填充 event_ts，不允许随意留 null
2. 后台回填任务：那 32 条有线索就持续往 `event_ts_backfill.jsonl` 补充（append-only，不改主记录）
3. **未来出现大量新增 null = 入库 bug**，按 bug 处理不是按数据现实处理

> 入库纪律：会话记忆 hook 自动传会话日期；语料回填传语料内显式日期；实在无线索才允许 null 且需在 source_ref 里说明来源（无来源的 null 属于待回填队列）。

## 补充维度（2026-11-09 同日扩契，用户追问"未来时间/项目区间/演进管理"后定）

### 维度4：未来时间 = 绝对时刻调度，不是相对时间解析
- 调度器 `scripts/scheduled_run.py`：schtasks 系统级注册（比进程内 sleep 可靠，进程挂了任务还在）
- 已注册示例：今晚 23:59 触发夜间管线（`schtasks /Query /TN CGV3_Nightly_2359` 可查）
- 触发落 `logs/schedule_log.jsonl`：计划时刻/实际触发/漂移秒数，可排查
- 边界：未来时间不进 event_ts（event_ts 只记已发生事件）；调度任务是一次性消费，不进记忆

### 维度5：实体时间区间（项目/模块的生命周期）
- 项目、模块（思维模块/记忆模块/SPI调试/8397等）= **跨多条记忆的聚合体**，不是一条记忆
- 实现：`data/memory/entity_timeline.jsonl`，每行 `{entity_key, label, born_ts, last_active_ts, member_inst_ids, status}`
  - born_ts = 成员最早 event_ts；last_active_ts = 成员最新 event_ts；新成员入库时刷新
  - member_inst_ids 用关键词聚合（脚手架期），后续可换 entity 链自动归并
- 与风险2的关系：实体区间天然解决"跨窗发酵"——项目级问题看区间，事件级问题看单点

### 维度6：演进时间线（"X 现在演变成什么样了"）
- `entity_evolution(entity_key, as_of)`：成员记忆按 event_ts 升序排成里程碑弧
- as_of 截止日支持"截至 5 月底时是什么样"的历史切片
- 无时间成员殿后排列（不丢弃），待回填后自动归位
- 实证：cognitive-engine-v3 实体 23 个里程碑，5月设计期(19条)→11月实施期(4条)演进弧清晰
